HybridCUA: Learning to Orchestrate GUI and CLI for Computer-Use Agents

Abstract

Computer use agents (CUAs) have demonstrated strong capabilities in completing digital tasks. However, existing CUAs either rely solely on graphical user interface (GUI) interactions, which are often inefficient and error prone, or augment GUI interactions with application specific APIs or tools, which require substantial engineering effort and are difficult to scale across applications. We argue that the next generation of CUAs should combine GUI interactions with the command line interface (CLI), leveraging the generality of the GUI and the efficiency of shell commands. A critical challenge, however, is that current models do not know when or how to use the CLI during task execution. To address this challenge, we develop a data construction pipeline that produces three types of trajectories: GUI only, CLI only, and interleaved GUI and CLI trajectories. This pipeline results in HybridCUA-8K, containing 5K hybrid trajectories and 3K verified RLVR tasks. Building on these data, we propose a training framework with two stages: supervised fine tuning on the constructed trajectories, followed by reinforcement learning with our CLI aware rewards that encourages agents to use the CLI selectively and reliably. Experiments show that HybridCUA-9B achieves 53.6% accuracy on OSWorld, improving over the base model by 14.8 percentage points, and improves performance on WindowsAgentArena by 4.0 percentage points. These results demonstrate the effectiveness and cross platform generalizability of the hybrid GUI and CLI paradigm for computer use agents.

Contributions

  1. A scalable hybrid data pipeline

    HybridCUA-8K: 5,000 GUI-only, CLI-only, and interleaved trajectories plus 3,000 verified RLVR tasks, each labelled by whether CLI use offers a clear execution advantage.

  2. Interface choice as a training signal

    SFT on the trajectories, then RLVR with two CLI-aware rewards that separately target routing errors (choosing the wrong interface) and execution errors (issuing a command that fails).

  3. A 9B model that gains from the shell

    HybridCUA-9B reaches 53.6% on OSWorld, +14.8 points over its base model, and transfers to an MCP environment and to Windows. Trajectories, tasks, pipelines, and the model will be released.

Access to a shell is not the bottleneck

Handing a capable MLLM a shell does not help — it hurts. Every one of four representative agents loses accuracy on OSWorld once the CLI is exposed, by 2.5 to 11.5 points, and their CLI usage scatters from 0.15% of steps to 67%. Some grind through GUI sequences a single command would replace; others reach for the shell too eagerly. HybridCUA-9B uses the CLI about as much as the most CLI-heavy baseline, yet gains 14.8 points where that baseline loses 6.6.

Two gaps in how CUAs are trained

The data never shows what hybrid behaviour looks like. GUI, shell, and code corpora are each abundant but siloed: CUA datasets contain almost exclusively GUI actions, while terminal and code datasets omit the GUI context in which commands are issued.

The supervision is blind to interface choice. Step-level imitation favours locally plausible actions and outcome rewards merely check task completion; neither can tell a well-chosen interface from a successful but inefficient path.

Method

Hybrid supervision need not be collected from scratch: many GUI action sequences admit an equivalent shell command. HybridCUA exploits this to build data across three execution schemas, then makes interface choice explicit in the reward.

One action space, two interfaces

Rather than exposing separate GUI and CLI tools, every executable interaction goes through the same bash action. A direct shell command and a quoted Python heredoc of pyautogui calls are both just commands, so switching interfaces costs the model no extra grammar. The wrapper is a representation, not a reclassification: PyAutoGUI through bash is still a GUI action.

At step t the agent observes the current screenshot and, when the preceding action was a direct command, its stdout/stderr. CLI-only trajectories therefore restrict the action interface, not the observation modality — they still contain screenshots.

Ablating this choice matters: keeping the two interfaces in distinct tools (computer_use and cli) costs 7.2 accuracy points against the unified schema under matched training.

GUI action
bash(command="""python3 <<'PY'
import pyautogui
pyautogui.click(500, 400)
pyautogui.hotkey('alt', 'f')
PY""")
CLI action
bash(command="""python3 <<'PY'
import docx
d = docx.Document(p)
run.font.size = Pt(12)
d.save(p)
PY""")

Plus the control actions wait, terminate and answer. Coordinates are predicted in a 1000×1000 space and mapped to the display at execution time.

Stage I — supervised warm-up

The three trajectory types are combined into 𝒟SFT and serialised as an instruction followed by observations and actions in the unified format, optimising next-token prediction over agent-generated responses. They supply complementary supervision: GUI control, shell command syntax, and interface routing. Expanding each trajectory at every decision step yields 52,227 samples, 46,876 after filtering to a 12,000-token context; at most three screenshots are kept per prefix, the current one at full resolution and two downsampled.

Stage II — CLI-aware online RL

A plain accuracy reward gives weak credit for interface choice: successful rollouts score the same despite unnecessary switches, and a failed command goes unpenalised if the task eventually completes. HybridCUA adds two signals at complementary granularities.

Task level · when

RCLI = 𝟙[Success(τ)] · 𝟙[b(τ) = b★]

Every RLVR task carries a label b★ for whether CLI use has a clear execution advantage, obtained by sampling 16 rollouts per interface mode and ranking them. A successful rollout is rewarded only when its CLI usage matches that label, so the model learns to reach for the shell selectively — not maximally.

Added to the trajectory reward with λCLI = 0.1, before group normalisation.

Step level · how

rtexec = −1 if the command fails, else 0

Terminal feedback localises the blame. A shell-level execution failure penalises exactly the tokens of the action that caused it, so command reliability improves without muddying the trajectory-level signal. Non-CLI steps get zero.

Added to the normalised GRPO advantage with λexec = 0.3, on the responsible action's tokens only.

Training configuration

HybridCUA-8K

5,023 supervised trajectories over 11 application domains and three interaction modes, plus 3,000 RLVR tasks that each ship an executable verifier and a reachable target state. Trajectories average 10.4 logical steps (median 7, p90 22).

GUI only

Converted demonstrations

Open-source UI-MOPD trajectories are re-expressed action by action as equivalent pyautogui calls inside the unified bash wrapper, preserving the original GUI supervision.

CLI only

Skill-guided rollouts

Per-application CLI skills are distilled from documentation and reference code; a Qwen3.8-27B agent in a Claude Code harness solves CUA-Gym tasks with the shell alone, and successful rollouts are kept.

Interleaved

Free switching & GUI→CLI rewriting

One route lets the agent choose between both interfaces during execution. The other folds terminal-typing segments of GUI trajectories back into single commands, replays the result, and keeps only successful replays.

RLVR task pool by domain (3,000 tasks)

Results

Main results on OSWorld

HybridCUA-9B reaches 53.6% accuracy in 14.0 average steps — best on both metrics among comparably sized models. Merely exposing the CLI cuts steps by 9.5 but accuracy from 38.8% to 18.4%, so the shorter trajectories reflect early failure, not efficiency. Trained, the second interface pays off at both stages: 46.0% vs 44.2% after SFT, 53.6% vs 50.4% after RL. Both branches share the same base model, comparable SFT corpora, and identical RLVR tasks and RL steps.

Out-of-distribution generalisation

Two axes of transfer, reported separately. On OSWorld-MCP, HybridCUA-9B scores 47.1%, 9.1 points over Qwen3.5-9B and on par with API-integrated ToolCUA-8B. On WindowsAgentArena it reaches 36.0%, +4.0 over its base model — issuing PowerShell commands despite training only on Linux shells, which suggests what transfers is when to delegate to a shell rather than memorised commands.

What the model learns to route where

Interface choice tracks the interaction the task actually needs. The CLI dominates OS tasks (84% of steps), where commands reach files and system settings directly; the GUI dominates Chrome (74%), where the work lives on a rendered page.

Reading the split

Content editing (85.8% CLI) and result verification (98.4% CLI) suit direct data manipulation and state inspection — reading a saved file back is something a command does exactly and a screenshot does approximately.

Spatial adjustment (58.4% GUI) goes the other way: positioning and layout need the visual feedback loop that the screen provides.

Information gathering splits nearly evenly, which is the point — neither interface wins categorically, so the routing decision has to be learned per situation.

Cooperation, not just coexistence

In an essay-formatting task the two interfaces cooperate at two levels. Across the trajectory, GUI steps focus the Writer window and open its menu (step 7) while CLI steps use python-docx to apply 12-point text and single, double and one-and-a-half line spacing before saving (step 10). Within a single step, step 13 dismisses the menu with pyautogui and then reopens the saved file through the shell to check font size and spacing — both in one bash call.

Code

The release has two halves: env_infra serves desktop environments over an HTTP session protocol, and online-rl runs GRPO against them (slime + Megatron-LM for the actor, SGLang for rollout). The trainer never launches VMs itself; it only speaks HTTP to an env server.

Clone and build the training environment on a GPU node with nvcc:

# build the training venv (compiles flash-attn / apex / TE in place)
git clone https://github.com/ZJU-REAL/HybridCUA.git
cd HybridCUA
bash online-rl/install_env.sh

Start an environment server from env_infra, then launch the run on the head node:

WANDB_API_KEY=<your-key> \
HF_CKPT=/path/to/sft/checkpoint \
GUI_ENV_SERVER_URL=http://127.0.0.1:19000 \
  bash online-rl/gui-rl/scripts/HybridCUA-9B_16gpu_fully_async.sh

Each additional worker node joins the same Ray cluster:

RAY_HEAD_ADDR=<head-ip> WORKER_NUM_GPUS=8 \
  bash online-rl/gui-rl/scripts/gpu_worker_join_ray.sh

Keep the three concurrency knobs aligned — the real ceiling is their minimum: SGLANG_SERVER_CONCURRENCY × num_engines (the in-flight pool), GUI_FAST_ROLLOUT_PROCS (the worker pool), and GUI_TRAJECTORY_CONCURRENCY (env sessions). All default to 64. online-rl/gui-rl/config.py is the single source of truth for every GUI_* variable.
